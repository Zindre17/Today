# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`today` is a single-project .NET 10 console app packaged as a **dotnet global tool** (`ToolCommandName: today`). It tracks what you worked on during a day: `start`/`end` named tasks, `did` for one already finished, `rm` for one logged by mistake, `show` the day as a Gantt chart, `list` past days, `clear` state, `theme` the output, `help` and `version`.

## Commands

```bash
dotnet build
dotnet run -- <args>               # e.g. dotnet run -- start coding, dotnet run -- show
dotnet pack -c Release             # produces ./nupkg/Today.<version>.nupkg
dotnet tool install --global --add-source ./nupkg Today
```

**`dotnet run` writes the user's real day.** State moved out of `bin/Debug/net10.0/` in 2.0,
so a development run is no longer isolated from the installed tool. Point both overrides at a
scratch directory before running anything:

```bash
export TODAY_DATA_DIR=/tmp/today-data TODAY_CONFIG_DIR=/tmp/today-config
```

There are no tests and no test framework in the repo; verification is done by running the CLI.

Styling is suppressed whenever stdout is redirected, so piping into a file or `cat` shows plain text. To see the colors from a tool call, allocate a pty: `script -qec "dotnet run -- show" /dev/null | cat -v`.

`TreatWarningsAsErrors` is on and `Nullable` is enabled — any nullable warning fails the build.

`README.md` is the user-facing counterpart to this file, and is packed into the nupkg via
`PackageReadmeFile`, so it doubles as the nuget.org listing — a change visible to someone
*using* `today` belongs there as well as here. `Today.csproj` also sets `RepositoryUrl`
explicitly rather than leaving it to SourceLink, so the package still says where it came from
when the git query is skipped (see the `release` skill on the sandbox and `.gitmodules`).

`Taste` (the persistence library) is a separate repository, `~/code/Taste`, by the same author. A
change here that needs one there is two sessions, not one — ask before working in it. A `PreToolUse`
guard enforces that.

## Architecture

**Persistence via `Taste`** (NuGet `Taste` 2.1.0, https://github.com/Zindre17/Taste — the same author's, and per-taste pantries were added to it for this app). `Cook.Serve<T>()` hands back a `T` — what was kept last time, or a fresh one — and `.Savor()` (the extension form of `Cook.Preserve`, from `using Taste.Savoring;`) writes it back. Key consequences:

- **`Serve` never returns null**, so nothing here checks for it or writes `??= new`. A taste therefore has to be able to make itself: parameterless constructor, defaults as property initializers — which is why `Day`, `History` and `Theme` all initialize their properties and none of them is a positional record.
- **`Savor` takes the taste itself**, not a handle, so it keeps whichever object it is called on — and `Savor<TTaste>` resolves the jar from the *static* type. That is why `Target` exists (`Target.cs`): a day out of `History` is a `Day` like any other, so savoring one directly would write it over the day in progress, silently and with no way back. Where a day came from travels with the day, and `Target.Keep()` is the only thing that writes.
- A malformed file makes `Serve` **throw** rather than fall back to a fresh taste — state that cannot be read is a thing to go and look at, not to quietly overwrite. Nothing catches it, so a hand-edited jar surfaces as a `JsonException` stack trace.
- Files are named `<assembly>.<full type name>.json` — namespace and all, so with everything in namespace `Today` that is `today.today.day.json`, `today.today.history.json` and `today.today.theme.json`. `Taste` builds that name privately; nothing here reproduces it, deliberately (see `Storage`).
- **A taste's type name is therefore on disk.** Renaming or moving one silently orphans what it kept — no error, no fallback, just a fresh taste where the data used to be. That is what `Taste` 2.0's switch to the *full* name did to every jar here, and it is why `Today` was renamed to `Day` before 2.x was ever published rather than after. `Taste` offers no way to pin a jar name to something other than the type, so a rename is a migration until it does.
- **Where they live is `Storage`'s decision, not `Taste`'s default.** `Storage.Arrange()` calls `Cook.UseKitchen` with two pantries: `Pantry` (the data directory) for `Day` and `History`, and a per-taste pantry for `Theme` (the config directory). Days are records the user cannot reconstruct; the theme is a preference they could retype — that is the same split the OS makes, so it is the one used. On Linux that lands at `~/.local/share/today/` and `~/.config/today/`.
- `Serve` returns a cached instance per type, so all call sites in a run share one object and there is no handle to pass around. Nothing is written unless `Savor()` is called.
- **A kitchen is settled once per process and cannot be changed after the first `Serve`**, which is why `Storage.Arrange()` is the first statement in `Program.cs`, ahead of `Cook.Serve<Today.Today>()`. Serving first would settle the default kitchen — state beside the executable — and `UseKitchen` would then throw rather than move it.
- **Nothing is written unless something asks for it.** There is no `finally` around the dispatch any more: each command calls `Target.Keep()` at the point it changes the day, so `show`, `list`, `help`, `version`, `complete` and every failed command leave the files untouched. Up to 2.0 the `finally` meant all 43 paths through the CLI rewrote the day, `today help` included — that was a consequence of where the call sat rather than a decision, and a read-only command that writes state is one serialization bug away from losing a day. `History` and `Theme` were never covered by the `finally` and still savor themselves; `today.today.theme.json` is only written once `theme set`/`theme reset` runs.
- **`RollOverIfNewDay` writes the fresh day itself**, and must. Nothing downstream will now, and a stale day left in the jar would be archived again — and warned about again — on every command until something happened to be logged.

**`Storage` owns the locations** (`Storage.cs`). `TODAY_DATA_DIR` and `TODAY_CONFIG_DIR` override the OS defaults, and they are what makes a development run safe: state no longer lives in `bin/Debug/net10.0/`, so a bare `dotnet run` writes the **real** day. Set both to a scratch directory when exercising anything (the `release` and `verify-output` skills do). An OS location that comes back empty throws rather than quietly putting the day in the working directory.

**Moving off the executable directory was done by hand, once.** Up to 1.11.0 state sat beside the running binary (`~/.dotnet/tools/` for the shim, `bin/Debug/net10.0/` under `dotnet run`) under the pre-2.0 names `today.today.json`, `today.history.json`, `today.theme.json`; 2.0 both moved the directory and — because `Taste` 2.0 names a jar by the taste's *full* type name — added a segment to every file name. There is **no migration code**: the author moved and renamed their own three files and that was the whole population. Nothing looks beside the executable any more, so a leftover pre-2.0 file there is invisible rather than dangerous. Anyone else arriving with 1.x state renames by hand — and, since 2.1, converts the two day files from the `DateTime` shape to the `DateOnly`/`TimeOnly` one, which `README.md` carries a script for. `Serve` throws on the old shape rather than falling back, so an unconverted jar is a `JsonException` stack trace on every command, not a quiet empty day:

```
today.today.json    -> ~/.local/share/today/today.today.day.json
today.history.json  -> ~/.local/share/today/today.today.history.json
today.theme.json    -> ~/.config/today/today.today.theme.json
```

**Model** (`Day.cs`, `Doings.cs`, `History.cs`): a `Day` is a `DateOnly` plus a `List<Doing>`; a `Doing` is `What` + a `TimeOnly` `Start` + a nullable `TimeOnly` `End` (null = still running). `History.Days` is a `Dictionary<DateOnly, Day>`. `System.Text.Json` handles both types natively, `DateOnly` as a dictionary key included, so no converter is registered anywhere.

**The types are `DateOnly`/`TimeOnly` because `DateTime` was wrong twice over.** A `DateTime` carries an offset, and it is read back: a jar written in `+02:00` and read in UTC deserialized `Date` to the *previous* day, so rollover archived the day in progress under yesterday's key and handed back a blank one — a timezone change silently ate the day. Task times shifted with it, so a 09:00 task read as 07:00. The second problem was quieter: a `Doing` carried a date that had to equal `Day.Date` with nothing keeping the two in step, which made the day-boundary invariant something to check rather than something the storage could not express. Neither is checkable now, because neither is representable.

`show <date>` / `clear history <date>` go through `TryParseDay`, which returns a `DateOnly`, so a time typed alongside the date is dropped by the type. It used to have to be dropped by hand — carrying it through made `show "2026-08-12 10:00"` report no history and `clear history "…10:00"` succeed at doing nothing.

**A task belongs to the day it is logged on.** `Day.Date` says so, `History` is keyed by it, and the chart's window is drawn from it, so a task outside it breaks all three at once — the axis degenerates and the duration column overflows. `on` widens *which* day is being written to but not this: the day a task lands on is still the day named, and every check below is against that day rather than against today. A task now has no date to be outside its day *with*, so the only remaining way in is a duration: `Did` refuses one longer than the time since midnight. That check is asked of the duration rather than of the resulting start, because backing a `TimeOnly` past midnight wraps it to the far end of the same day instead of failing. `TryParseWhen` still refuses a date spelled out that is not the day being worked on, since that is a claim the argument can make even though the model cannot store it. The second hid better, because every time reported back is `HH:mm` — `did x 100h` used to answer "from 17:10 to 21:10" without mentioning that the 17:10 was four days ago.

**Output and theming** (`Output.cs`, `Theme.cs`, NuGet `Fansi` 0.0.3 by the same author as `Taste`). Every console write goes through `Output`, which is the only place that touches `Fansi`. `Theme` holds one `ThemeStyle` per output element (header, task, running, bar, axis, duration, date, success, warning, error) and stores colors **by name** so the JSON stays readable and an unknown name degrades to the default rather than failing to load; `Theme.Get`/`Set` look elements up reflectively, so adding a property to `Theme` extends `theme set` automatically — and equally, an element nothing in `Output` reads is a setting the user can change to no effect, which is what `time` was until it was dropped. Removing one needs no migration: the now-unknown key in an existing `today.today.theme.json` (in the config directory) is ignored on load and disappears on the next write. Errors and warnings go to **stderr** and everything else to stdout, so `today show > day.txt` captures the chart and not the reason there wasn't one; `Output.Warn` is stderr-but-not-a-failure — the command carries on and its exit code is unchanged, which is why it styles itself apart from `error` rather than sharing it; the two streams are redirected independently, so `Plain` and `PlainError` each ask about their own and `Format` takes which one to use. `Output.Format` builds a `Fansi.OutputFormat` per style and is also where column width and ellipsis truncation live — `Doing` has no `ToString` override, so this is the single renderer.

**`summary` adds up several days at once** (`Summary` in `Program.cs`, `Output.Summary`): `summary <span>`, `summary <day>` or `summary <from> <to>`, one row per task rather than one row per day. `show` answers a day at a time and `list` only says which days exist, so "how much of last week went on this" could not be asked. Days come out of `History`, plus the day in progress when the range reaches it — today is never in `History`, so it is added rather than found. Each day is measured against its own reference, the same rule `show` draws by, which is why the totals cannot simply be taken over a flat list of `Doing`s: a stretch means nothing except against the day it happened on.

`spans` pairs each word (`week` 7, `month` 30, `year` 365) with its length, so the command and `complete summary` cannot disagree — the same reason `shells` and `commands` are each written down once. `TryParseSpan` also takes `<count><unit>` for `d` and `w`, and is **quiet on failure** because the caller tries a day next and one complaint naming both forms beats two naming one each; that is what `TryParseDay`'s `complain` parameter is for. Spans are **rolling and inclusive of today** — `week` is today and the six days before it. A calendar week would need a convention about which day starts one, and on a Monday morning would answer with a few hours rather than with the week that was meant. Rows are ordered **longest first**, unlike the chart's start order, because a summary is asked in order to find where the time went and start order means nothing once days are stacked.

**`show` draws a Gantt chart** (`Output.Chart`): one row per *name* — name, how long it took, then the bar — with time on the x axis. `--no-chart` renders the same day through `Output.Rows` instead: the same rows and the same total without the bars or the axis. `Chart`, `Rows` and `Summary` all go through `Row`, `Total` and `Took`, which is the point of those being extracted — three renderings of the same work that disagreed about a number would be worse than having only ever offered one. `Took` is the single definition of how long a set of stretches came to, and is public because `Summary` reckons its days up in `Program.cs` before handing totals back to be drawn. Tasks are grouped by `What`, so a name logged more than once (`did` allows it, and work picked up again is the same work) draws every stretch of itself on one row and sums their times; `GroupBy` keeps first-appearance order, which is start order because `Insert` sorts. Grouping is ordinal, matching how `end` and `rm` match a name, so `Alpha` and `alpha` stay separate rows. The total is unaffected — it was always the sum over every entry. The duration column is right-aligned and `Spell` writes it the way `did` accepts it (`45s`, `15m`, `1h30m`), so a time the chart reports can be typed straight back in; the total sits in that same column, which is why it reads as their sum rather than as the sentence it used to be. Both are styled with the `duration` theme element, including on a running row, so the column stays a column. **Every measurement in the chart is a `TimeSpan` since midnight, not a `TimeOnly`**, and that is deliberate: the window's closing edge rounds *up* to the next whole hour and so can be 24:00, which is a real position on the axis that a `TimeOnly` cannot hold — it wraps to 00:00, making `to < from` and collapsing any day ending after 23:00 to a one-hour chart. `TimeOnly` subtraction is circular too, so a span measured backwards returns about 23 hours rather than a negative, which turns an obviously broken number into a plausible one. `Clock` writes a `TimeSpan` out as `HH:mm` by hand, since a `TimeSpan` of exactly one day formats its hours component as `00`; the axis therefore closes on `24:00` rather than `00:00`, which is also the truthful label for the right-hand edge of a single day. `Window` rounds out to whole hours so labels land on the hour; a local `Column` function maps a moment to a chart column; `Axis` places the closing label first and lets intermediate ticks yield to it, so the label at the chart's edge is always truthful; `TickStep` picks the smallest interval whose `HH:mm` labels still fit. Bars use `█`, unfinished ones `▓` drawn up to `Finish` (now for the current day, the last thing that happened for a day out of history — never backwards, or a task started ahead of that moment would measure negative). Any stretch, even a zero-length one on the closing edge, gets at least one cell. Because one row can now hold both finished and running stretches, `Bar` emits the line a run at a time so each keeps its own style and the gaps stay unstyled; where stretches of a name overlap the running one wins the cell, so a row that is still going says so all the way to its edge. `ChartWidth` derives from `Console.WindowWidth` (80 when redirected, since it throws without a terminal) and reserves room for the overhanging final label so nothing wraps; it is measured against `Indent`, so widening the name or duration column narrows the chart automatically. Below about 59 columns the chart hits its minimum of 20 and the row is wider than the terminal. In plain mode (`NO_COLOR` set, or `Console.IsOutputRedirected`) the same format is built without colors, which emits no escape sequences while keeping the padding.

**Day rollover** runs in `RollOverIfNewDay` (`Program.cs`) once before dispatch, so every command sees a current day: if the loaded `Day.Date` isn't today, the old day is pushed into `History` (and `Savor`ed) and a fresh `Day` replaces it. A stale day with no tasks is discarded rather than archived, so `list` doesn't fill with blanks.

**A day archived with something still running is warned about** (`WarnAboutUnfinished`), because rollover is the only moment the tool knows a task is running on a day that is ending. The task goes into history with `End` still null, and `Output.Chart` measures an unfinished task only up to the last thing that happened on its day — usually that task itself, being the one that was forgotten, which draws it as a single cell worth `0s` and totals the day short with nothing saying how much is missing. Warning is all that is done: an end that was invented (midnight, or the last known moment) is a number the user would later trust, and this codebase refuses elsewhere rather than guessing. It fires once — the next rollover is a no-op — which is accepted, since that showing lands while the user can still remember when they actually stopped.

**Command dispatch** is a list-pattern `switch` expression in `Dispatch(Target, string[])` in top-level statements in `Program.cs`; each command is a local function taking the day it works on plus the remaining arguments, and returning the process exit code. The day is **passed in rather than reached for** — that is what lets `on` hand one command a different day without changing what any of the others mean, and it is why no command closes over an ambient `today` local any more. The `commands` table at the top holds each one's name, argument syntax and one-line description, and is the single source for both readers of it: `complete commands` takes the names, and `help` prints the table. So a new command means a dispatch arm, a local function, a row in `commands` — plus a `Complete` case and a name in `today.bash`'s `case $cmd in` list if its arguments are completable — and a place in `amendable` if `on` should accept it.

Bare `today` and an unknown command both fall through to `help`, so the command list has one renderer rather than a second terse copy. An unknown command prints its complaint to stderr first, then the table to stdout.

**Shell completion** (`completions/today.bash`). The file is an `EmbeddedResource` with `LogicalName="completion.bash"`, and `today completion bash` copies that stream straight to stdout — bytes as they are, since re-encoding a script is a way to change it. That is the whole reason the command exists: someone who ran `dotnet tool install` has no checkout to copy a script out of, and `dotnet`'s own completion (`dotnet completions script bash`) only ever covers `dotnet`'s subcommands, never a tool invoked under its own name. The file stays the editable source, so there is no second copy in C# to drift; a test that the emitted bytes still match `completions/today.bash` is the thing to run after touching either. `shells` in `Program.cs` lists what `completion` accepts and is also what `complete completion` offers, so the command and its own tab-completion cannot disagree; each name pairs with a `completion.<shell>` resource. The script holds no knowledge of its own: it asks the binary via the hidden `complete` command — `today complete commands` for the command list, `today complete end` for the tasks currently running, `today complete did` for the ones already finished, `today complete rm` for every distinct name on the day, `today complete show` (and `complete on` and `complete summary`, the same list) for the days in history, plus the words that name one of them — so `today end <TAB>`, `today did <TAB>`, `today rm <TAB>`, `today show <TAB>` and `today on <TAB>` each offer exactly what that command would accept. `did` offers finished tasks only: it would accept a running name too, but what you want for one of those is `end`. Only the *first* argument of a command is completed, so `today on <date> end <TAB>` offers nothing rather than offering today's tasks for another day's command; making it offer that day's tasks needs `complete` to take a day too, and is deliberately left for later. `complete show` offers history only, never today's own date: `show` with no argument is today, and `show <today>` would look in `History` and find nothing. It offers `yesterday` and the weekday names alongside the dates, but only those that land on a day there is history for — `monday` with no Monday behind it would complete to an error, which is the opposite of what completion is for. The script passes `$cmd` straight through **and `$argc` after it**, because one command needs to know which argument is being completed: `summary <from> <to>` takes a day in either position but its span words belong to the first only, and offering `week` where only a date will do completes to an error. Every other case ignores the extra argument. `summary` is also why the script's "first argument only" rule has an exception — for it, `argc <= 1`.

**`on <date> <command>` is completed the whole way through**, which is the one place the script has structure of its own rather than asking. It cannot ask, because the shape is positional: when word 1 is `on`, word 2 is a date (`complete on 0`), word 3 is the command (`complete on 1`, which offers `amendable` rather than the full list — `on list` would complete to a refusal), and everything past that is an ordinary command sitting two words to the right. So `base` shifts to 3, the argument count is taken from `base + 1`, and the date is carried along as a **third argument to `complete`**, which moves every candidate onto that day: `today on monday rm <TAB>` offers Monday's tasks and `today on monday end <TAB>` offers what was left running on Monday, which is the case `on` exists for. A day that does not parse, or that history does not hold, yields nothing at all — a half-typed date is a normal thing to be looking at, not an error to report into the middle of a command line.

`_today_reply` exists because that dequoting-and-re-escaping is now wanted at three call sites rather than one, and a task name with a space in it has to survive all three. so a new completable command needs a `case` in `Complete` and its name in the `case $cmd in` list. `Complete` writes raw lines with `Console.WriteLine` rather than through `Output`, and is deliberately left out of the `commands` table since it is for scripts. Task names contain spaces, so the script dequotes the word readline gives it before matching and re-escapes each candidate with `printf %q` (unless the user opened a quote, where raw names complete inside it). Changing the command list means editing `commands` in `Program.cs` only.

**Exit codes**: 0 on success, 1 on any user error — unknown command, missing or unparseable argument, "already doing X", "not started doing X". `Day.Start`/`Day.End` return `bool` for this reason. `help` (also `--help`, `-h`) and `version` (also `--version`) are the exception in the other direction: they print to stdout and exit 0, because being asked for them is not a failure. Bare `today` prints the same help at exit 0 — showing someone the commands is not a failure either, and there is nothing to report as one. `version` reads the assembly version, so `<Version>` in the csproj is what it reports.

Arguments are positional after flags are filtered out (`IsFlag`), so `start -c x` and `start x -c` behave the same: `start <what> [when]`, `end [what] [when]`, `did <what> <duration> [when]`. Times go through the `TryParseWhen` helper, which prints a message and fails the command rather than falling back to `DateTime.Now`. It takes a *moment on the day being worked on* — outside that day, or still to come, and it is refused — while `TryParseDay` takes *a date*, any date, for the commands that name a day.

A bare `17:30` has to mean a time on the day being worked on, not on today, or `on yesterday end coding 17:30` would place the end tomorrow-of-that-day and be refused by its own check. `TryParseWhen` parses with `DateTimeStyles.NoCurrentDateDefault`, which leaves a string that named no date sitting on `0001-01-01` — the only way to tell a bare time from one that spelled a date out. A spelled-out date has to match the day being worked on; either way only the `TimeOfDay` is kept.

**The future check is guarded by `target.IsToday`, and has to be.** With a `DateTime` a past day never tripped it, because the comparison carried a date. A `TimeOnly` carries none, so `on yesterday end coding 23:30` would read as the future purely because 23:30 is later than the clock right now. `TryWhen` wraps the whole optional-time argument, since `start`, `end` and `did` differ only in which positional slot it sits in.

`TryDefaultWhen` is the other half: **only today has a now.** A command on a past day that leaves the time out is refused rather than defaulted to the real clock, which would put the task on the wrong day.

`TryParseDay` also takes `yesterday` and the weekday names. A weekday means the most recent day it fell on and **never today** — naming the day you are standing in means the one a week back, since today is reachable without naming it and has nothing in history to name. The letters-only guard before `Enum.TryParse<DayOfWeek>` is load-bearing: that overload also accepts the numbers behind the names, so without it `show 3` would quietly become Wednesday. The future check compares by the minute, so the minute in progress counts as now; anything finer would reject `start x 14:23` over the seconds spent typing it.

`did <what> <duration> [when]` records a task that ran for `<duration>` and ended at `[when]`, or now if that is left out — for the things you only remember to log afterwards. The end can be said out loud because "now" is not always available (a past day has none) and because a run that finished earlier was never expressible: `did coding 2h` could only ever mean the two hours ending this minute. `TryParseDuration` accepts a run of number+unit pairs (`15m`, `2h`, `1h30m`; s/sec, m/min, h/hr/hour, case-insensitive) and rejects everything else rather than guessing — a bare number has no unit, so it fails. Values are capped at a week by the parser, and then `Did` refuses any duration that would put the start before midnight, so the effective cap is the time since. Note that a leading `-` makes an argument a flag, so a negative duration never reaches the parser. Unlike `start`, `Day.Did` does not refuse a name that is already running: logging what you just did says nothing about what you are doing.

**`on <date> <command>` runs one command against a day already filed away** — the repair path for the day you forgot to close. History was otherwise write-once: rollover puts days in, `show` reads them, and the only way to change one was `clear history`, which deletes the lot, so a task left running had no fix short of editing the jar by hand.

It is one dispatch arm that resolves the date, builds a `Target` and re-enters `Dispatch`, so every command it forwards to is the same code working on a different day. `amendable` lists what it accepts — `start`, `end`, `did`, `rm`, `show` — and the rest are left out for want of a meaning rather than out of caution: `list` and `theme` are not about a day, `clear` and `completion` already say what they act on, and `help`/`version` would answer the same thing twice. `on` is absent from its own list, which is what refuses `on monday on tuesday …`.

A date that turns out to be **today** is forwarded to the day in progress rather than looked up, because today is not in `History` yet and a lookup would report no such day. `show` resolves its own optional date the same way, for the same reason.

`rm <what>` deletes a task from the day — the mistyped `start`, the `did` with the wrong duration. `Day.Remove` uses `FindLastIndex`, and since `Insert` keeps `Tasks` in start order that is the latest-starting match, which is the one just logged; running or finished makes no difference. It works on whichever day `Target` names, so `today on yesterday rm typo` reaches into `History`; deleting a whole past day is still `clear history <date>`.
